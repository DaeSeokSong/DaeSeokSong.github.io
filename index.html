01 / CURRENT RESEARCH

Swappable modules

Can a trained network hand a functional part to another network without relearning everything? Three lines of work, each starting from the limit of the one before.

The long-term aim is an AI system whose parts people can inspect, replace, and when necessary remove. What I have measured so far is narrower: that parts can be swapped and aligned. Pick a line to see its idea, its architecture, and what the experiments have shown so far.

It started from the Plug-in modules idea in my 2024 KSRR paper (second author; the paper’s author statement lists my contribution as data acquisition and interpretation, and I carried out the algorithm work from devising the method through implementation, training and experiments). Lines 1 and 3 use public datasets only; line 2 grew out of a problem in my day job. The wider question came from re-reading Hinton’s GLOM and Forward-Forward work and asking what it would take for a learning system to be modular while staying cheap in memory and energy. I built a research harness on Claude Code (agents, skills and hooks) to check derivations and architectural claims against the literature. I set the questions, the pre-registered criteria and the decisions.

RevolverNet: swap and load modules in a trained network

Take a classifier made of detachable modules, move one module in from a separately trained network, and see whether it still works.

Idea and concept

A classifier is split into slots. Each slot holds a module, which I call a bullet, that owns a group of classes and has its own readout. A router, the trigger, sends each input to the responsible slot. The cylinder is the set of slots, a chamber is one slot, and loading means putting a new bullet into an empty chamber. Two questions: can a module from another network be swapped in, and can a new module be loaded into an empty slot while the loaded ones stay untouched?

How it works

The class groups are assigned by me before training, so the modularity is imposed by structure, not learned. A naive swap fails because two networks trained from different initializations use different feature coordinates. An orthogonal rotation estimated from the two modules’ outputs on the same 512 input images from a validation split (orthogonal Procrustes) maps one set of coordinates onto the other with no retraining. Loading freezes the loaded modules and their readouts and trains only the new module; the router may be re-tuned.

Results so far

99.4–99.8% of the accuracy lost under naive swaps was recovered by the rotation, with no retraining, in each of three structures (99.41, 99.84 and 99.63% before rounding; CIFAR-10, single seed 42).

Two-module image classification. In each structure the four models shared the dataset, architecture and role assignment and differed only in initialization (Kaiming, orthogonal, uniform, sparse). Recovery is a share of what naive swapping lost, not of the original accuracy. Aligned swaps stay slightly below the intact models (by 0.3, 0.1 and 0.1 points). C scores lower in absolute terms because two held-out classes are trained to be rejected and count as errors, so accuracies are not comparable across structures, and I make no claim about detecting unknown inputs.

  • Initialization alone did not make naive swaps work. In an earlier test on a mixture-of-experts variant, naive swaps stayed near 38% (37.7–38.0%) whether the models shared an initialization, were initialized independently, or shared one for five epochs before diverging (three runs per condition; CIFAR-10, two modules). Orthogonal alignment then brought them to 89.6–90.3%, level with the intact models (89.7–90.3%). Alignment is still setting-dependent: with a standard backbone trained by backpropagation on CIFAR-100 (two modules, three seeds), naive swaps were already close to intact (64.5–64.7% against 65.1–65.5%).
  • An earlier five-seed proof of concept recovered 86% of the loss, 9.9 points above a control that applied the same rotation to the opposite module. Its pre-set verdict was partial success; a three-seed look had suggested full success before the extra seeds corrected it.
  • One attempt failed its pre-set check: a learned “unknown” output meant to signal when a new module is needed (it over-selected “unknown”).

Limits

Every figure in the table comes from one seed (42), so run-to-run variation was not measured; a pre-set check that the four intact models perform alike failed narrowly (a 2.5-point spread against a 2.0-point limit). The result shows that mismatched coordinates are one cause of swap failure, not that modules are compatible across datasets, architectures or class assignments, which I have not tested. Roles are assigned, not emergent, so I describe each module’s share of the classes as imposed. Aligning independently trained networks already has a literature (model stitching, re-basin, relative representations) and module-level control has precursors (Gradient Routing, SteerMoE), so I claim none of this as new. This is preliminary, unpublished work.

Cartridge: load only the task heads a deployment needs

Train one body once, make every task a removable head, and let the operator choose which heads to load at each site.

Idea and concept

The starting point was a production problem. The same medical radiograph product is deployed to several sites, and each site wants a different set of functions. In a multi-task model the task heads are entangled through the shared body, so every change of function set meant retraining and revalidating the whole model. Cartridge asks for the opposite: one body, trained once, with each function as a head, a cartridge, that can be loaded or left out, so that training and validation end at the head. There is no router; choosing what to load is handed back to the operator, because a router that chooses can send an input into the wrong module.

How it works

The body is trained on an initial set of tasks and then frozen. Each head reads only the body’s features and never another head, which is what makes removal safe. Three requirements were written down first: a site can pick any subset of heads and each keeps its full-build performance; a new head trained later on the frozen body should come close to training everything together; and if the body is replaced by one trained with the same recipe, the existing heads should still work without retraining. The tests, their margins and the pass rules were fixed before the runs. The first version gave every task group its own network stream. Readouts that fused several streams were dropped after removal tests showed that taking one stream out hurt other tasks, and the later version moved to one shared body with removable heads.

Results so far

  • Removal is free by construction. When each head reads only the body’s features, removing a head leaves the others exactly unchanged. That follows from the wiring, not from learning, so I do not count it as evidence of modularity.
  • Attaching a new task to a frozen body (new tasks, two head types, with and without dense tasks in the body’s training set; three seeds each) recovered 40–96% of the gap between a body with no task training and one trained together with the new task. The frozen body never reached the jointly trained one within the pre-set margin, in all eight settings; the closest missed it by 1.2 times the margin. Mapping the frozen body’s features into the strong body’s coordinates and reusing its head did not close the gap either: it did worse than training a new head. That points to information missing from the body rather than mismatched coordinates (six of the eight settings were valid for this test, and it covers linear readouts only).
  • Moving a head to another body trained with the same recipe but a different seed failed mostly because the feature coordinates differ. A linear map fitted without labels recovered 86–109% of the transfer loss (log-loss, three body seeds). F1 recovered less, falling short by 0.02–0.07 in 10 of 12 comparisons, and values above 100% come from the map shrinking the features, not from added information.
  • An “interpreter” into a shared feature space did not work. Encoders that map any backbone into a common space missed their pre-registered criteria: trained without labels, all six judged bundles failed. Adding the head’s own loss brought the loss within the bar, but only for heads used in training (a head it had not seen failed), and F1 still fell short in 25 of 40 cells, and a per-class bias correction rescued nine of those 25. These runs used a single seed, and the nine-cell rescue was recorded before an independent check.

Status: on 12 October 2026 I closed the version-2 design and decided to redesign it from the data and task definitions up. The lessons carry into Expert Synapse.

Limits

Three seeds at most and few new tasks; the margins themselves rest on three seeds and are unstable. Data, backbone and sample-size details are omitted on this page. Several favorable-looking numbers are structural: zero leakage and zero removal loss in the fully separated version come from the wiring, and I do not cite them as modularity or emergence.

Expert Synapse: attach a trained head to an unseen frozen backbone

Keep a large pretrained vision transformer frozen and link experts on its blocks to a task head, so that a head trained on one backbone can attach to a different backbone without retraining.

Idea and concept

RevolverNet and Cartridge moved modules between networks I train myself. Expert Synapse asks the same question for large pretrained backbones that stay frozen, so the parts to exchange are the small ones around them. At each backbone block I attach a small bundle of experts, and the task head gets its own entrance experts. Features are rewritten as similarities to a fixed set of anchor tokens (relative representations, Moschella et al., 2023), and an expert’s “signature” is how it responds to those anchors. When a head moves to a new backbone, the links between the two sides are computed once from the signatures, not relearned.

How it will be judged

Four controls sit in the same slot: (a) a learned adapter layer per backbone pair, (b) a closed-form orthogonal Procrustes translation, which is the alignment used in RevolverNet, (c) relative representations alone, and (d) experts alone. The pass rule is fixed in the approved design before the main runs: the moved head must reach the accuracy of the backbone it was trained on, minus a tolerance, and the accuracy of a label-trained link on the new backbone, minus a tolerance. The tolerances come from bootstrap standard errors and are set before training. The test bed is public COCO 2017 (box, mask and keypoint heads), and a negative outcome will be reported as one.

Results so far

In progress No results yet on performance, transplant or emergence.

  • Two earlier routes were closed after missing their pre-set bars: a fixed “convention” encoder, which reached about 0.6 of the detection floor (COCO AP 0.195 against a 0.322 floor; under-fitting, single seed, selection set), and a learned translator into a shared feature space failed its pre-registered criteria (see Cartridge).
  • Stage 0 (head choice between a single-scale FCOS and a DETR-family head on five backbones, per-block probes, sanity checks) was implemented and pre-registered by 22 October 2026. As of 23 October, the official keypoint-model evaluation and the five block-probe runs are done, the keypoint gate run is under way (6 of 26 epochs, not a verdict), and the ten head-check runs have not been launched. Keypoints enter the claim only if a directly trained head clears a floor set at 70% of the official reference score; otherwise they are dropped.

Limits

I do not claim novelty over relative representations (Moschella et al., 2023) or closed-form Procrustes translation between models (Maiorca et al., 2023); a literature search did not find a dense-feature (detection or segmentation) precedent, which is a statement about my search, not about the field. I do not claim emergent modularity either: the anchor form and routing rules are imposed by design, and whether roles emerge from learning alone is untested.

WHERE THIS IS GOING

AI that is efficient, and that people can control

The three lines above are steps toward a learning system whose structure stays understandable and controllable as it gets more capable: cheap to run, and made of parts that people can find, adjust, and, if they cause harm, remove without breaking the rest. What counts as harmful, and how to separate it into parts, is an open problem that I do not claim to have solved.

  1. GOAL

    Remove risky roles, keep the useful ones

    Find which module, expert, neuron or head carries a role, then remove the parts responsible for harmful or dangerous behavior while the useful parts keep working. I have not yet measured whether removing a module suppresses an unwanted behavior, and module-level control already has precursors (Gradient Routing, SteerMoE).

  2. DIRECTION

    Efficiency, with ideas from the brain

    Structures and learning rules that cut compute, memory and training cost. This is a direction, not a result: combining GLOM and Forward-Forward did not raise accuracy for me, and in one same-recipe comparison (image classification, three seeds, one structure) a rule that sends error back through a separately learned feedback path trailed backpropagation by about 13 points (77.5% against 90.8%). Learning feedback paths already has prior work, so I claim nothing new there. I have only tried spiking networks lightly (in July 2026, a surrogate-gradient network and a transport-free learning rule on spikes); the rule stalled well below the surrogate-gradient network, and I did not take it further.

  3. UNTESTED

    Roles that emerge instead of being assigned

    Today I assign the roles. Whether modular roles can arise from learning alone is untested, and it is the planned follow-up.
